# 作品追加・Instagram更新ガイド

人間は投稿URLや素材を渡し、Codexが取得・命名・文章整理・画像登録・検証を担当します。**slug、管理用ID、JSON、Markdownを人間が用意する必要はありません。**

このガイドは現在のリポジトリの運用手順です。Instagramからの取得はCodexが利用可能なブラウザ等で行い、保存済みデータを既存コマンドで取り込みます。投稿URLだけで取得が完了するかは、その投稿を閲覧・取得できる環境によります。

## 1. 人間が渡すもの

| 依頼 | 最低限渡すもの | 指定があるときだけ添えるもの |
| --- | --- | --- |
| Instagramから新規追加 | 本人の対象投稿URL。複数まとめて指定可 | 本文にない担当情報、掲載画像の指定、下書き指定 |
| Instagramの既存作品を更新 | 対象投稿URLと、最新内容を反映したい旨 | 維持したい手修正、更新対象を限定する指示 |
| Instagramを使わず新規追加 | 作品名と掲載画像。担当内容も短く添えるとスムーズ | 掲載日、クライアント、クレジット、公式URL、画像順、下書き指定 |

画像はチャットへの添付、またはCodexが読めるローカルフォルダのパスで渡せます。作品名・画像・担当が資料から分かる場合は、資料を渡すだけでも構いません。担当の詳細が不明でも登録できますが、カテゴリすら判断できないときはCodexが必要な点だけ確認します。

### コピーして使える依頼文

**Instagramから追加**

```text
次の本人のInstagram投稿をポートフォリオに追加してください。
［投稿URLを1行に1つずつ記載］

docs/works-guide.md に従い、slugの命名、重複確認、画像取得、
概要・担当・altの整理、取り込みと検証まで進めてください。
```

**既存投稿を更新**

```text
次の投稿の最新内容を既存の作品ページへ反映してください。
［投稿URL］

公開URLは維持し、手修正を残しながら必要な差分だけ反映してください。
```

**素材から新規追加**

```text
次の作品をポートフォリオに追加してください。
作品名：○○
画像：添付画像／ローカルフォルダのパス
担当：スチール撮影

slug・カテゴリ・紹介文・altは資料に基づいて整えてください。
掲載日は指定なし。画像順は添付順でお願いします。
```

「下書きで保存」「先頭はこの画像」「掲載日は○月○日」など、通常と違う希望だけ付け足してください。公開サイトへの反映まで依頼する場合は「検証後、公開まで進めてください」と添えます。

## 2. Codexに任せること・既定の扱い

| 項目 | Codexの対応 |
| --- | --- |
| 作品名 | 本人の投稿・資料から読みやすい表示名に整理。正式な作品名は保持 |
| `slug` | アーティスト名・作品名などから短い英小文字名を作り、衝突を検証。候補を毎回人間に選ばせない |
| `workId`・フォルダ | 既存コマンドで生成。再取得なら既存のものを再利用 |
| カテゴリ | 本人が担当した仕事に基づいて選択。MVという作品形式だけで `movie` と決めない |
| 掲載日時 | Instagramは元投稿の日時。手動追加で指定がなければ追加時の日本時間をサイト掲載日時として使用し、完了時に伝える。制作・撮影日時とは区別 |
| 画像順 | Instagramはカルーセル順、手動追加は指定順・添付順。フォルダだけならファイル名順。先頭が一覧用画像 |
| 概要・担当 | 投稿・資料の確認できる事実から `summary` と `role` を記入。担当が分からなければ空欄 |
| alt・注釈 | 実画像を確認して具体的なaltを作成。人物名など、画像だけでは確認できない情報は推測しない。注釈は必要な場合のみ |
| クライアント・クレジット | 明記された情報だけ記入。出演者や制作会社をそのままクライアント扱いしない |
| 公開対象 | 掲載用として依頼され、内容と画像が揃った作品は `draft: false`。下書き指定や掲載に必要な情報が不足する作品は `draft: true` |

Codexは、取得可能な情報を先に確認し、任意項目が空欄という理由だけで作業を止めません。取得できない画像・日時、カテゴリの判断に必要な情報など、実際に進行を妨げる不足だけをまとめて確認します。

### slugの命名ルール

- 英小文字・数字・単語間のハイフンのみ、64文字以内。例：`artist-song-making`、`artist-name-photo`。
- 公式の英字表記があれば使い、なければ読みやすいローマ字にする。人間への命名確認は不要。
- 同名の別作品は、根拠のある `-photo`・`-making` 等で区別し、それでも重複する場合は `-2` などを付ける。
- 公開済み作品だけでなく、下書きのslug・別作品の旧フォルダURLとの衝突も検証する。
- **既存作品を再取得するときは命名し直さない。公開済みのslug・フォルダ名・workIdは固定する。**

## 3. Instagramから追加・更新する手順

以下はCodexが実施する作業です。人間がターミナル操作やexport作成を行う必要はありません。

1. `README.md` と `AGENTS.md` を読み、既存の `works/*/index.md` の `workId`・`source` と投稿IDを照合する。表示名だけで新規・既存を判定しない。既存なら対象の `index.md` と `instagram.json` を開く。
2. 指定された本人の投稿を開き、本文全文・投稿日時・元投稿URL・カルーセルの画像順を確認する。動画は掲載用のカバー画像を取得する。現在のギャラリーは画像掲載用で、動画ファイルの取り込み・再生には対応していない。
3. 画像と取得した本文を `.imports/instagram-update/` など作業ごとのフォルダへ保存する。取得できなかった投稿は未取得として残し、既存作品を削除したり、不明な日時や画像順を補完したりしない。
4. タイトルとカテゴリを確認し、新規作品だけslugを命名する。取得したテキストや画像パスからプログラムで `export.json` を生成する。長い本文をJSONのエスケープ文字列として手作業で編集しない。
5. 次のdry-runで追加・更新の対象、slug衝突、画像の読み込み、手修正の保護結果を確認し、問題がなければ同じexportを取り込む。

   ```bash
   npm run import:instagram -- .imports/instagram-update/export.json --dry-run
   npm run import:instagram -- .imports/instagram-update/export.json
   ```

6. 生成・更新された `index.md` を確認し、事実に基づく `summary`・`role`・画像ごとの `alt` を追記する。必要に応じて本文の見出しを整え、クレジットを確認する。**これらの追記はインポーターの自動機能ではなく、Codexが行う編集。**
7. 新規取り込みは初期状態が **`draft: false`**。下書き依頼の場合や情報が不足する場合は、取り込み直後に `index.md` を `draft: true` に変更する。既存作品のdraft状態は取り込みで維持される。
8. 「5. 検証・公開・完了報告」まで進める。

### Codexが作るexportの項目

ルートは1件以上の投稿を含むJSON配列です。ファイル形式の例は [READMEのexport形式](../README.md#exportjson-の形式) を参照してください。

| 項目 | 必要性・内容 |
| --- | --- |
| `url` | 必須。本人のInstagram投稿URL。`p` / `reel` / `tv` 形式に対応 |
| `date` | 必須。元投稿のタイムゾーン付き日時。例：`2026-10-01T12:00:00+09:00`。取り込み時に日本時間へ統一 |
| `caption` | 必須。取得した元投稿本文。空文字不可 |
| `files` | 必須。ダウンロード済み画像の配列。掲載順に並べる |
| `files[].path` | 必須。画像のローカルパス。作業ディレクトリに依存しない絶対パスを推奨 |
| `slug` | 新規のみ必須。Codexが命名。既存作品は保存済みslugを維持 |
| `title` | Codexが確認して指定する。省略時には既存取得記録または本文から補完される |
| `categories` | Codexが確認して指定する。省略時の推定に任せきりにしない |
| `files[].cover` | 動画のカバー画像かどうかの取得記録。これを `true` にしても先頭へ移動しない。表示順は `files` の順序で指定 |
| `folder` | 通常は不要。新規フォルダ名を明示したい場合のみ |

`summary`・`role`・`client`・`alt`・`draft` はexportからは反映されません。取り込み後に公開用の `index.md` を編集します。

### 再取得で手修正がある場合

- インポーターは投稿IDで照合し、手で変更した項目・本文を保護する。
- alt・caption・並び順を追記・変更した画像は、`images` 配列全体が保護される。再取得で新画像が保存されても、ギャラリーへ自動追加されない場合がある。
- 「最新内容を反映」と依頼された場合は、Codexが最新の `instagram.json` と `index.md` を比較し、手修正を維持して必要な項目・画像だけ反映する。
- 投稿の再取得記録は `instagram.json`、サイト本文の正本は `index.md`。サイト修正のために取得記録を書き換えない。
- `summary`・`role` が最新本文と矛盾しないかも確認する。取得対象に含まれない作品はそのまま残す。

## 4. Instagramを使わず新規追加する手順

1. 提供された作品名・素材を既存作品と照合し、同じ作品の追加編集か、新しい作品かを確認する。
2. Codexがslugを決め、次のコマンドで下書きを作る。IDとフォルダはコマンドに生成させる。

   ```bash
   npm run new:work -- "作品タイトル" --slug artist-title
   ```

3. 画像を生成先の `works/<作品名>/img/` に配置し、`images` 配列へ掲載順に登録する。元の素材は保持する。対応形式はJPEG・PNG・WebP・AVIF。別形式しかない場合は表示を確認しながら対応形式へ変換する。
4. `index.md` のカテゴリ・掲載日時・概要・担当・alt・本文を、資料に基づいて整える。生成直後のカテゴリ `photo` は仮の初期値なので、必ず実際の担当と照合する。
5. 「作品の概要を記入します」等のひな形文を実際の文章に置き換える。情報がない見出しは削除し、未確認のクレジットで埋めない。
6. 掲載用の内容・画像が揃ったら `draft: false` にする。下書き依頼の場合は `true` のままにする。
7. 「5. 検証・公開・完了報告」まで進める。

### 最終的なindex.mdに必要な情報

この表はCodexの確認用です。人間が全項目を記入する必要はありません。

| 項目 | 必須／任意 | 用意する方法 |
| --- | --- | --- |
| `workId` | 必須 | コマンドが生成。変更しない |
| `slug` | 公開時必須 | Codexが命名・重複確認。下書きのみ空欄可 |
| `title` | 必須 | 指定された作品名、または資料の正式名 |
| `categories` | 必須・1つ以上 | `photo` / `movie` / `production-staff`。実際の担当に応じて複数可 |
| `publishedAt` | 必須 | タイムゾーン付き日時。Instagramは元投稿、手動は指定日または追加日時 |
| `draft` | 運用上必ず確認 | `false` でサイトの生成対象、`true` で除外 |
| `images[].file` | 公開時1枚以上必須 | `img/01.jpg` 等。ファイルの存在と順序を確認 |
| `images[].alt` | 任意・新規登録時に推奨 | Codexが実画像に基づいて作成。省略時は作品名＋連番 |
| `images[].caption` | 任意 | 注釈が必要な画像だけ記入 |
| `summary` | 任意・推奨 | 作品と本人の関わりを短く整理。検索・SNSの説明にも使用 |
| `role` | 任意・推奨 | 確認できる担当のみ。例：スチール撮影、編集、制作進行 |
| `client` | 任意 | 資料に明記されている場合のみ。不明なら空欄 |
| 本文 | ひな形を残さず整理 | 概要・担当・クレジットなど、確認できる内容だけ記載 |
| `source` / `sourceLabel` | 任意 | 元投稿や公式ページがあれば指定。リンクのない作品も追加可 |

画像寸法・canonical・OGP・構造化データ・サイトマップは自動生成されます。作品ごとのOGP画像は不要で、共通ロゴを使います。新規作品を一覧へ表示するための手動リンク追加も不要です。トップの代表作に入れる場合だけ、別途 `src/config/site.ts` の `featuredWorkIds` を編集します。

一覧用のWebPサムネイルも、手動追加・Instagram取り込みのどちらでも `images` の先頭からビルド時に自動生成されます。サムネイルの手動作成・登録・コミットは不要です。幅400・800・1200px（元画像より大きくしない）の候補を生成し、表示サイズに応じて配信します。先頭の並び替えや画像の差し替えは次回の `npm run verify` / ビルドで反映されます。元画像と作品詳細用の画像は維持します。

トップの代表作にも同じWebPを使います。`featuredWorkIds` に指定した作品は高精細画面向けに1680・2520pxの候補も自動生成します（元画像の幅が上限）。代表作の変更時も画像の手動書き出しは不要です。

## 5. 検証・公開・完了報告

1. Codexが作品Markdown・画像・差分を確認する。公開URL、担当の事実、画像順、ひな形の残存をチェックする。
2. リポジトリ直下で以下を実行し、失敗した場合は原因を修正する。

   ```bash
   npm run verify
   ```

3. ローカルサーバーで新規・更新した詳細と作品一覧を確認する。表示の変更を伴う場合はトップ・プロフィール・スマートフォン幅・カテゴリ絞り込みも確認する。
4. 「追加・更新」は、通常ここまでのローカルでの掲載準備を指す。**`draft: false` にするだけでは公開サイトは更新されない。** 公開まで依頼されていれば、検証済みの依頼対象の差分を所定のGit運用で `main` に反映・pushし、GitHub Actionsの成功と公開ページを確認する。すでに依頼された工程の確認を繰り返す必要はない。
5. 完了報告は「追加／更新した作品」「確認用URLまたはファイル」「検証結果」「下書き・ローカル準備済み・公開済みのどの状態か」「未取得・不足があればその箇所」を短く伝える。

作業途中のダウンロード・exportは `.imports/` またはリポジトリ外に置きます。取得できない部分があれば、必要な画像・本文・日時など、その部分だけ人間へ補助を依頼します。slugやJSONの作成を人間へ差し戻す必要はありません。

実装の詳細は [README.md](../README.md)、編集時の共通ルールは [AGENTS.md](../AGENTS.md) を参照してください。
